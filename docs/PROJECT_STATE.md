## Current Focus

The current focus is the rotation simulator foundation needed for accurate conjures, commands, and equipment swaps.

Immediate design direction:

- introduce ordered same-tick user actions
- model timeline actions as ordered items per tick
- process user-authored ability and buff placements through ordered dispatch
- keep system-driven events in their existing tick lifecycle unless a rule requires moving them
- add equipment preset and slot swaps after the first ordered-action slice is stable

## Current Mental Model

The simulator should distinguish:

- user-authored ordered actions
- system-driven tick events

User-authored ordered actions include:

- ability casts
- ability releases
- buff placements
- future preset swaps
- future individual equipment slot swaps

System-driven events include:

- ability completion and release processing
- scheduled hit landings
- buff expiry
- cooldown ticking
- recurring conjure scheduling
- post-hit effects

The first refactor should be an orchestration change, not a rewrite of every processor.

## Current Preferred Timeline Direction

Preferred model:

- `Map<Integer, List<TimelineAction>>`
- `TimelineAction` as a sealed simulation-domain interface
- one concrete action record per payload type
- each action has `tick` and `order`
- each action wraps one placement or swap payload

Preferred package:

- `com.rotdb.simulation.domain.model.timeline`

Initial variants:

- ability cast timeline action
- ability release timeline action
- buff timeline action

Future variants:

- preset swap timeline action
- equipment slot swap timeline action

The user should not manually assign order in normal UI flows. Order should be generated by the layer that builds or
persists the rotation timeline, then treated as authoritative by simulation.

## Current Ability Cast And Release Direction

Ability casts and ability releases should be modeled as separate user-authored timeline actions.

Current combat understanding:

- a cast can occur when the action is otherwise valid
- most abilities release immediately after cast
- some abilities can be stalled by the user and released later
- stalled release timing is user-controlled, not an ability-defined delayed release
- only one ability can be stalled at a time
- casting another unreleased ability usually overwrites the currently stalled ability
- releasing and then casting on the same tick must be representable by ordered timeline actions
- casting and immediately releasing on the same tick must also be representable by ordered timeline actions

Likely simulation state concept:

- a stalled ability record containing the original placement identity and enough ability context to release it later

Current damage timing assumption:

- damage calculation snapshots on release, not cast
- no known ability needs cast-time damage state stored for later release
- stalled ability state should therefore identify the releasable ability, not preserve a cast-time damage snapshot

Current stalled-state lifecycle assumption:

- `StalledAbility` is runtime simulation state, not a timeline input generated for every placement
- an ability placement expands into cast and release timeline actions
- a cast action may create or overwrite `StalledAbility` when the release tick is later than the cast tick
- an immediate cast-and-release ability should leave no stalled ability after its release resolves
- a later cast may overwrite or clear an existing stalled ability according to combat rules
- stalled ability state should persist across ticks until released, overwritten, invalidated, or combat is dropped
- release actions should validate against the current stalled ability before resolving damage

This should be implemented as a V1 foundation only where needed for accurate behavior, not as a broad refactor for style.

## Current Conjure Direction

Necromancy conjures should follow these intended rules:

- conjure creation requires an active offhand with `NECROMANCY_CONDUIT`
- conjure maintenance requires an active offhand with `NECROMANCY_CONDUIT` or `NECROMANCY_SHIELD`
- removing a maintaining offhand for more than zero ticks should hard-remove conjures
- swapping away and back on the same tick should preserve conjures
- commands should warn or invalidate when the matching conjure is absent

The current implementation has been moving toward this but still needs ordered equipment-state support before the behavior
can be fully proven.
